# 운영 설계

서비스를 실제로 운영할 때를 가정한 설계 시나리오다. **아직 구현하지 않았다.** 지금 코드는 서버 한 대로 동작한다.

다루는 내용:

1. 연결이 끊겼다 다시 붙었을 때 데이터를 맞추는 방법
2. 서버를 여러 대로 늘리는 방법
3. 로그와 메트릭으로 상태를 보는 방법
4. 장애가 났을 때 대응하는 방법

## 0. 운영 환경 (AWS 가정)

| 역할 | 사용할 서비스 |
|---|---|
| 요청을 서버들에 나눠 줌 | ALB (로드 밸런서) |
| 앱 서버 | ECS (서버 한 대 = 태스크 하나, 1 vCPU) |
| DB | RDS for MariaDB (장애 시 예비 DB로 자동 전환되는 Multi-AZ) |
| DB 연결 관리 | RDS Proxy |
| 서버끼리 실시간 정보 공유 | ElastiCache for Redis |
| 로그 | CloudWatch Logs |
| 메트릭 저장 | Amazon Managed Prometheus (AWS가 운영하는 Prometheus) |
| 대시보드, 알림 | Grafana, CloudWatch 알람 → Slack |

- 개발할 때는 `docker compose`로 Prometheus를 필요할 때만 띄워서 본다.
- 운영에서는 Prometheus 서버를 직접 설치하지 않는다. 앱의 `/metrics`를 수집기(ADOT)가 읽어 AWS로 보낸다.

## 1. 재연결 시 데이터 맞추기

> **핵심:** 서버는 끊긴 동안의 메시지를 다시 보내 주지 않는다. 클라이언트가 "마지막으로 받은 번호(seq)" 이후를 요청해서 채운다.

모든 이벤트는 세션 안에서 1, 2, 3… 순서 번호(seq)를 받는다. 이 번호만 있으면 무엇이 빠졌는지 알 수 있다.

**클라이언트가 할 일**

1. 세션별로 마지막으로 받은 seq를 저장해 둔다.
2. 다시 연결되면 **먼저 구독(`session:subscribe`)** 한다.
3. 그다음 `GET /sessions/{id}/events?afterSeq=마지막seq`로 빠진 이벤트를 받는다.
4. 같은 seq가 두 번 오면 하나는 버린다.
5. 보냈는데 응답을 못 받은 메시지는 **같은 `clientEventId`로 다시 보낸다.**

**왜 구독을 먼저 하나?**
조회를 먼저 하면 "조회 끝 ~ 구독 시작" 사이에 온 메시지를 놓친다. 구독을 먼저 하면 메시지가 두 번 올 수는 있어도 빠지지는 않는다. 두 번 온 것은 4번에서 걸러진다.

**서버가 보장하는 것**

| 상황 | 결과 |
|---|---|
| 같은 메시지를 다시 보냄 | 한 번만 저장된다. 기존 메시지를 돌려준다. |
| 저장 도중 끊김 | 전부 취소되어 아무것도 남지 않는다. 다시 보내면 된다. |
| 저장 후 전달 전에 끊김 | 저장은 되어 있으므로 3번 조회로 받는다. |

## 2. 서버 여러 대로 늘리기

> **핵심:** 데이터는 MariaDB에만 저장한다. Redis는 서버끼리 "지금 누가 연결돼 있는지", "이 메시지를 누구에게 보낼지"를 공유하는 데만 쓴다.

**역할 나누기**

| 무엇을 | 어디에 | 이유 |
|---|---|---|
| 요청 분산 | ALB | 서버들에 골고루 나눈다. |
| 메시지, 세션 상태 (영구 데이터) | MariaDB | 순서 번호와 중복 방지를 DB가 책임진다. 서버가 몇 대든 결과가 같다. |
| 메시지 전달 대상 | Redis | A 서버에서 저장한 메시지를 B 서버에 연결된 사용자에게도 보내야 한다. |
| 접속 상태(online/offline) | Redis | 한 사용자가 여러 서버에 탭을 열어 둘 수 있다. |

**지금은 서버 메모리에 있어서 바꿔야 하는 것**

| 항목 | 지금 | 서버 여러 대일 때 |
|---|---|---|
| 메시지 전달 | 서버 메모리 | Redis로 다른 서버에 전달 (socket.io Redis adapter) |
| 접속 수 세기 | 서버 메모리 | Redis 카운터 |
| 서버 재시작 시 접속 상태 정리 | 전체를 offline 처리 | 자기 서버의 연결만 정리 |

- Redis가 죽어도 **메시지는 유실되지 않는다.** 실시간 전달만 잠깐 끊기고, 클라이언트는 1장 방법으로 채운다.
- 메시지를 저장하는 코드는 바뀌지 않는다. 바뀌는 것은 실시간 전달 부분뿐이다.

**메시지 순서**
여러 서버가 메시지를 보내면 클라이언트에 도착하는 순서가 섞일 수 있다. 그래서 클라이언트는 **seq 순서대로 정렬해서 보여 주고**, 번호가 비면 1장 방법으로 채운다.

**주의할 점**
- DB 연결 수: 서버 1대당 최대 10개다. 서버가 늘면 연결도 늘어나므로 RDS Proxy로 묶는다.
- 서버를 늘려도 **한 대화방의 처리 속도는 그대로**다. 같은 대화방의 저장은 DB가 한 줄로 세우기 때문이다. 늘어나는 것은 동시에 처리할 수 있는 대화방 수다. 1:1 채팅이라 문제되지 않는다.

## 3. 로그, 메트릭, 추적

| 종류 | 도구 | 무엇을 보나 |
|---|---|---|
| 로그 | NestJS `Logger` → CloudWatch Logs | 에러, 전달 실패 같은 "무슨 일이 있었나" |
| 메트릭 | Prometheus → Grafana | 요청 수, 응답 시간, 저장 실패 수 같은 "얼마나" |
| 추적 | 사용 안 함 | 요청 흐름이 단순해서 메트릭으로 충분하다. 서비스가 여러 개로 나뉘면 도입한다. |

**알림 기준 (예시)**

| 알림 | 조건 |
|---|---|
| 서버 다운 | 정상 서버 수가 기대보다 적음 (2분) |
| 에러 증가 | 5xx 응답이 1% 넘음 (5분) |
| CPU 과부하 | CPU 80% 넘음 (10분 계속) |
| DB 연결 부족 | DB 연결이 최대치의 80% 넘음 |
| 저장 느림 | 메시지 저장 시간 상위 5%가 200ms 넘음 (5분) |
| 저장 실패 | 저장 실패가 생김 |
| 전달 실패 | 실시간 전달 실패가 생김 |

## 4. 장애 대응

모든 장애를 같은 순서로 다룬다.

- **감지:** 무엇을 보고 알아채나
- **완화:** 원인을 고치기 전에 일단 서비스를 살린다
- **복구:** 원인을 고쳐 정상으로 되돌린다

### 4.1 서버가 죽음

| 단계 | 할 일 |
|---|---|
| 감지 | 정상 서버 수 감소 알림, 5xx 증가, 접속 수 급감 |
| 완화 | ECS가 새 서버를 자동으로 띄운다. **배포 직후라면 원인을 찾기 전에 이전 버전으로 되돌린다.** 서버가 여러 대면 남은 서버가 요청을 받는다. |
| 복구 | 로그로 원인을 찾는다. 코드 문제면 고쳐서 재배포하고, 메모리 부족이면 메모리를 늘린다. |

- 사용자는 재연결(1장)로 자동 복구된다.
- 죽은 서버에 연결돼 있던 사용자는 offline으로 정리된다.

### 4.2 서버가 느림 (CPU 과부하)

| 단계 | 할 일 |
|---|---|
| 감지 | CPU 80%가 10분 이상 계속, 응답 시간 증가 |
| 완화 | 아래 표에 따라 판단한다. |
| 복구 | 트래픽이 줄면 서버 수가 자동으로 줄어든다. |

| CPU 그래프 모양 | 의미 | 조치 |
|---|---|---|
| 계속 높음 | 평소 트래픽이 서버 용량을 넘음 | 서버 수를 늘린다 (자동 확장) |
| 산처럼 갑자기 튐 | 순간적으로 몰림 | 최소 서버 수를 올려 둔다 |
| 메모리도 같이 오름 | 메모리 부족 | 서버 메모리를 늘린다 |

- **서버 사양(CPU 코어)을 올려도 효과가 작다.** Node.js는 한 서버에서 CPU 코어를 하나만 쓰기 때문이다. CPU가 부족하면 서버 **개수**를 늘린다.
- 서버 개수를 늘리려면 2장의 Redis 구성이 **미리** 되어 있어야 한다.

### 4.3 DB가 느리거나 장애

| 단계 | 할 일 |
|---|---|
| 감지 | 저장 시간 증가, 저장 실패 증가, DB 연결 수 증가, RDS 장애 전환 알림 |
| 완화 | 오래 걸리는 쿼리를 중단한다. 연결이 모자라면 연결 수를 조정하거나 RDS Proxy를 둔다. |
| 복구 | 원인에 맞게 인덱스 추가, DB 사양 업, 읽기 전용 DB 분리 |

**원인 찾는 순서**

1. `SHOW FULL PROCESSLIST`: 지금 오래 걸리거나 기다리는 쿼리를 본다.
2. 슬로우 쿼리 로그: 느린 쿼리를 모아 본다.
3. `EXPLAIN`: 테이블 전체를 읽는지(풀 스캔) 확인한다. 그렇다면 인덱스를 추가한다.
4. 잠금 대기 확인: 같은 대화방에 요청이 몰려 줄이 길어졌는지 본다.

- DB가 예비 DB로 전환되는 1~2분 동안은 저장이 실패한다. 클라이언트가 같은 `clientEventId`로 다시 보내면 중복 없이 저장된다.

### 4.4 데이터가 사라지거나 안 맞음

대부분은 설계로 미리 막혀 있다.

| 문제 | 막는 방법 | 생겼을 때 |
|---|---|---|
| 같은 메시지가 두 번 저장 | `clientEventId` 중복 확인 | 일어나지 않는다. |
| 일부만 저장 | 메시지와 세션 상태를 한 번에 저장(트랜잭션) | 전부 취소되므로 다시 보내면 된다. |
| 메시지 전달 누락 | 순서 번호(seq)로 빈칸 확인 | 클라이언트가 빠진 것을 다시 받는다. |
| 세션 상태가 메시지 기록과 다름 | 같은 계산 함수(reducer) 사용 | 메시지 기록을 처음부터 다시 계산해 고친다. |
| 실제로 데이터가 사라짐 | 막을 수 없음 | RDS 백업으로 사고 직전 시점을 복원한다. |

**정기 점검 (미구현)**
- 세션마다 순서 번호가 1부터 빠짐없이 이어지는지
- 세션 상태가 메시지 기록을 다시 계산한 결과와 같은지

## 미구현 목록

- DB 연결까지 확인하는 헬스체크 `GET /health` (지금은 `GET /`뿐)
- Redis 기반 메시지 전달과 접속 수 세기
- 정기 데이터 점검 스크립트
